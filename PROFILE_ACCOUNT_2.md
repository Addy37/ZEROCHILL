# Profile + Account 2.0

## Backend deployment and account deletion

Apply `supabase/migrations/20260930212316_profile_account_2.sql` before shipping a client that requests `bio`, notification preferences, or shared creators. The migration adds a bounded public bio, owner-only notification choices, an intersection-only shared creators RPC, a live-session check, and explicit grants for existing social tables. It fixes pre-existing broad table grants that exposed protected profile columns and allowed recipients to edit DM fields beyond `read_at`. The older app keeps reading its existing profile columns and social tables. The notification preference row is optional; a missing row means all five categories remain enabled.

Deploy `supabase/functions/account-delete` with JWT verification enabled and server-only `SUPABASE_SERVICE_ROLE_KEY`. The Android client sends `POST /functions/v1/account-delete` with the signed-in user's bearer token and the JSON body `{"confirmation":"DELETE"}`. The function verifies the token with Supabase Auth, checks that its session ID still exists, deletes objects under that user's `avatars/<user-id>/` folder through the Storage API, then calls Auth Admin to hard-delete only the verified user. It returns `{"deleted":true}` on success. It never accepts a user ID from the request body and never returns privileged credentials. If Storage or Auth deletion fails, it returns an error and the account remains active for a retry. Partial avatar cleanup is safe to retry.

Current foreign keys hard-delete profile, creator favorites, comments, comment likes, video likes, block edges, direct messages, social reports, and notification choices after Auth user deletion. Existing comment `parent_id ON DELETE CASCADE` also removes other users' replies beneath deleted comments. A DM disappears from both participants' inboxes when either participant deletes an account. Reports involving the deleted user also disappear, including reports another person submitted. There is no retained conversation tombstone or moderation record in this schema. The app should state that conversations and replies involving the user can vanish before the final destructive confirmation. Deletion also invalidates refresh sessions through Auth cascade; an already-issued access JWT can remain cryptographically valid until its expiry, so the client must clear its local account session after success and privileged operations must authenticate the current user/session.

The avatar Storage cleanup matters: Auth deletion can fail while the user owns Storage objects. Do not delete `storage.objects` through SQL because that would leave the physical object orphaned. The function removes files via the Storage API.

Rollback before client release can remove `save_zerochill_notification_preferences`, `shared_zerochill_creators`, `current_zerochill_session`, the preferences table, the new bio constraint/column, and the Edge Function after disabling clients that call them. Keep the explicit least-privilege grants and owner-only favorite upsert policy; restoring the old broad grants would reopen the protected-field and DM-write issues. Once users have saved bios or preferences, dropping those columns/tables loses their data. Hard-deleted accounts cannot be restored by a migration. Production migration `profile_account_2` was applied as version `20260930213102`. The rollback-only SQL fixtures passed against the migrated schema. Edge Function deployment and device verification are tracked in the PR.

Run the rollback-only fixtures in `supabase/tests/profile_account_2.sql` against a migrated disposable database. Confirm actual policy and grant behavior under `anon` and `authenticated` roles before production rollout, then test one disposable account with an avatar and DMs end to end. Account deletion changes server data irreversibly and should be deployed only with the client ready to clear its session and present the two-stage confirmation.


## Android behavior and compatibility

Account keeps its existing entry point and auth flow. Profile save changes only display name and plain-text bio. Bio is optional and capped at 160 Unicode code points by the database and repository. Form drafts are scoped to the rendered account across recreation. The public profile has display-name-first identity, bio, self-edit routing, and shared creator count/list. Shared creators use only the server-side favorite intersection and disappear for either-direction blocks; there is no inferred interest system.

Notification choices sync to the account. They filter new in-app reply/like entries, foreground social banners, favorite creator entries, and app update entries. Existing history and message inbox/unread counts remain. Social push and DM alerts are not implemented, so the screen does not offer a misleading DM switch. The reserved direct_messages column defaults true for compatibility; it is not exposed as a current control. Android app-update permission/settings retain their existing separate behavior.

Creator favorites now keep separate account collections and a signed-out collection. The legacy local list imports once into the first account used after upgrade, then account switching cannot upload another account's local favorites. Existing installs that already mixed local favorites before this update cannot reconstruct their earlier per-account lists automatically. Deletion removes the deleted account's cached preferences/social history/favorite collection and session; local downloads, video favorites, playback history, backups, and general settings remain.

No application IDs, signing identities, remote source config, content source, player, or feed routing change. Before merge, device-test avatar crop, profile save/bio, public preview/layout, DMs, blocks/unblock, preference toggles, email confirmation, password update, deletion with a disposable account, keyboard, recreation, and account switching.
